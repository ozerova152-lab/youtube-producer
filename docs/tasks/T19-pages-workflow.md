## Описание

Решение принято в `docs/spec/02-tech-architecture.md`, раздел «Развёртывание» (2026-10-29): витрина
`site/` публикуется на GitHub Pages. Настройка Pages «из ветки» публикует только корень репозитория
или папку `docs/` (по знаниям автора спеки, на момент записи не сверено; исполнитель проверяет это
по документации GitHub), а страница лежит в `site/`, и `docs/` занята спекой. Поэтому нужен
workflow GitHub Actions, который публикует именно `site/`.

Что сделать:
- создать `.github/workflows/pages.yml` по критериям приёмки;
- добавить автотест (в стиле соседних тестов: читает файл, разбирает YAML, сети нет) на триггеры, права,
  путь публикации, отсутствие `secrets.` и наличие `concurrency`;
- дописать раздел в `docs/dev/setup.md`.

Ограничения и оговорки:
- Версии официальных действий и их входных параметров исполнитель сверяет по их страницам на
  GitHub в момент выполнения (веб-поиск), не по памяти; закрепление по полному хешу коммита против
  по тегу решить и записать в журнал задачи, с одной строкой почему.
- Сам запуск workflow проверить локально нельзя: он работает только на GitHub, в публичном
  репозитории и после выбора источника «GitHub Actions» в Settings → Pages. Пока репозиторий
  приватный, публикации не будет, а запуски workflow после пуша могут завершаться ошибкой на шаге
  публикации. Ошибки на этом шаге до публикации репозитория ожидаемы. Проверка в этой задаче
  статическая (тест на файл), живую публикацию человек проверяет сам по чек-листу спеки.
- Пушить на GitHub и включать Pages исполнитель не должен; это шаги человека.
- Ничего платного не подключается; секретов в workflow нет.
